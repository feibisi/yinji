# 印迹 Agent 可操作性二次审计（2026-08-09）

## 结论

印迹已经具备“受控 Agent 直接操作”入口：Agent 可先执行环境诊断，再用结构化命令完成视觉盖章、扫描件生成、证据校验和外部签名程序编排。它不应被描述为浏览器内数字签名系统，也不应接收或保管证书私钥。

当前准入范围是单机、本地文件、明确输入输出目录、人工或编排器提供印章素材。服务器上传、远程印章库、证书托管、静默覆盖和无人确认删除仍不在准入范围内。

## 本轮确定的边界

1. **视觉章与数字签名分离**：`stamp`、`scan` 只改变文档视觉内容；`sign` 只调用显式配置的外部程序。
2. **印章库默认仅会话保存**：新数据进入 `sessionStorage`；旧版 `localStorage` 数据只迁移到当前会话，不静默删除，用户确认后才清理旧副本。
3. **人工下载与 Agent 产物分离**：人工界面一次下载 `.yinji.zip`；Agent 输出 PDF 与 `.yinji.json` 两个独立文件，便于后续系统逐项消费和校验。
4. **默认不覆盖**：`stamp`、`scan`、`sign` 遇到已有输出时失败；只有明确传入 `--force` 才覆盖，`sign` 永远不允许输入路径等于输出路径。
5. **签名结果不冒充验签**：外部签名程序成功且返回非空文件，只证明编排完成；证书链、吊销状态和 PDF 签名有效性仍须独立验证器确认。

## Agent 操作面审计

| 能力 | 命令 | 结果 | 限制 |
|---|---|---|---|
| 能力发现 | `capabilities` | PASS | 返回 `yinji-agent-result/v1` |
| 环境诊断 | `doctor` | PASS | 同时验证应用身份和 CDP WebSocket 信息，不把任意 HTTP 200 当成功 |
| 视觉盖章 | `stamp` | PASS | 本地文件；输出 PDF + 证据记录；默认拒绝覆盖 |
| 扫描件生成 | `scan` | PASS | 本地文件；走批量扫描管线；默认拒绝覆盖 |
| 证据校验 | `verify` | PASS | 检查文件名、字节数和 SHA-256；不等于数字签名验签 |
| 外部签名编排 | `sign` | PASS | 外部命令必须显式配置；临时文件完成后原子替换；不保管私钥 |
| 状态与截图 | `state` / `capture` | PASS | 返回统一结果 schema；仍依赖本地 Chrome CDP |
| 回归诊断 | `smoke` / `scan-check` | PASS | 面向开发和巡检，不替代业务文件人工抽查 |

## 安全与恢复审计

- 浏览器返回的产物名必须是普通文件名，拒绝目录穿越。
- ZIP 条目拒绝路径分隔符和超出当前 ZIP32 范围的单项；人工证据包用系统 `unzip -t` 验证通过。
- 会话印章只接受 PNG、JPEG、GIF、WebP data URL，单项上限 8 MB；不把 SVG 或任意字符串持久放入印章库。
- `verify` 对篡改后的 PDF 返回失败和非零退出码。
- `stamp`、`scan` 在发现输出冲突后先整体拒绝，不产生部分覆盖。
- `sign` 使用同目录临时文件；成功后改名，失败后清理临时文件。输入和输出相同、未配置签名器、已有输出均明确失败。
- Agent 失败统一返回 `yinji-agent-result/v1` JSON 和非零退出码，便于编排器决定重试、转人工或终止。

## 本轮验证证据

- 全量浏览器单元测试：`124/124`，失败 `0`。
- `smoke`：上传、印章、添加对象、切换导出和导出提示均通过。
- `scan-check`：17 项检查全部通过，包括未访问页、方向、元数据、取消和独立批量扫描管线。
- `stamp` 与 `scan`：均生成 PDF 和 `yinji-evidence/v1` 侧车。
- `verify`：原始盖章件、扫描件通过；追加 1 字节后的副本在 size 和 SHA-256 两项失败，退出码 `1`。
- 覆盖保护：已有产物时退出码 `1`，原 PDF SHA-256 前后不变。
- `sign`：输入输出同路径、未配置签名器、输出已存在均退出 `1`；模拟外部签名成功，`--force` 成功且无临时文件残留。
- 人工下载路径：捕获到 `output.yinji.zip`，系统解压测试通过，包含 `output.pdf` 和 `output.yinji.json`。
- 存储迁移：旧数据成功进入会话，旧副本保留且警告可见；确认清理后旧副本删除、会话副本保留。
- `doctor`：真实应用与 CDP 通过；将普通 Markdown 的 HTTP 200 冒充应用时正确失败。

## 仍需保留的人在环环节

- 选择正确的印章主体、确认盖章权限和核对最终视觉位置。
- 提供并管理外部签名器、证书、PIN、时间戳服务和信任链。
- 决定是否使用 `--force`、是否清理旧印章副本、是否把结果上传到业务系统。
- 对正式合同执行独立 PDF 签名验证、业务审批和归档。

## 准入建议

可允许 Agent 在隔离工作目录内直接运行 `doctor → stamp/scan → verify`。正式流程必须固定输入目录、独立输出目录、签名器允许名单和日志留存；只有校验成功且人工确认主体/位置后，结果才能进入外部签名或业务归档。任何网络上传、证书托管或跨用户共享印章库都应作为独立项目重新做威胁建模和权限设计。
